# Architecture rules
- Movement list, period summaries and local provisioning share the first-competence lower bound; dashboard_movimentacoes mirrors it for all charts regardless of activation status. Preserve historical rows instead of deleting them.
- Closing preparation uses current repository documents by full context before Portal fallback; missing files are archived as imports, not emails. Explicit repository import is read-only until confirmation, rechecks versions and reuses attachment dedup by source ID/bytes. Stale work cancels; Portal has no competence filter and preparation reuses save. History is read-only, loaded on demand from the editor header, not the attachment list.
- Global surgery events are verified by one scheduled server-only fixed-upstream scan, deduplicated by demand/booking/date, and exposed through demand-inheriting RLS only to admin/executivo/executivo_externo; per-user read state feeds the existing bell/cards, never complaint resolution. Deep links temporarily isolate and focus the authorized row without erasing saved filters.
- Operational movement billing status and note-date lookups use only normal financial entries in the shared RPC, excluding first-month entries before attachment sharing and ranking so an initial invoice cannot imply a movement closing.
- Report sender settings store only nonsecret metadata in a singleton admin-RLS table; the settings form never verifies domains or enables delivery, which require the workspace email setup separately.
- Demand surgical alerts share a read-only React Query lookup by full CPF and beneficiary name, refresh every minute only for open forms/visible rows, and require explicit active status and a current/future date; never infer complaint resolution from booking. External agenda has no configured webhook, so polling and focus refetch provide automatic updates without changing stored demands.
- Movement life-report tracking stays movement-scoped; generation never alters operational or financial fields. Sends use fixed-upstream async Portal jobs; contract comes only from the selected row, re-read under user RLS before download/send, and every filename must contain exactly its contract marker. Batch candidates are frozen from filtered rows and ready-state is rechecked before email. The report dialog separates consultation from sending: consultation settles PDF and Excel through the same jobs, lists every successful file, keeps download failures visible and takes update dates only from upstream Last-Modified; sending still requires both files.
- Email history is server-written only after SMTP acceptance; repository imports are distinct and excluded from email counts/history. Archive bytes remain immutable in private movement-scoped storage; document writers share identity locks and preserve versions. Archive failure never re-sends or hides a completed email; legacy dates never imply a fabricated time or sender.
- Central adhesion uses the shared PDF reader and `compararExcelComPdf` as a distinct explicit-total category, with absent quantity recorded unverified; the description month is recorded separately from the movement competência and never blocks approval nor shifts dates, because some companies move in the month before billing.
- Surgical pending reports reuse the authenticated fixed-upstream agenda proxy and its server-only environment key; never embed a private credential in Vite environment variables or return it to the browser.
- Public CNPJ lookup runs through an authenticated read-only edge proxy with a fixed upstream URL; a review dialog applies nonempty results to existing permitted draft fields only after explicit confirmation, preserving secondary addresses and requiring the existing save flow for persistence.
- Automatic CNPJ status sync: every-minute cron calls `sincronizar-situacao-cnpj` in batches of 3 (public API rate limit), storing display-only results in `empresa_cnpj_situacao` (re-checked every 24h; transient failures are not persisted and retry next cycle); the cron authenticates with a token stored in `config_sync`, never an env key; the companies list renders badges from this table and the "Divergências CNPJ" filter derives from `divergenciaCnpj` — none of this ever writes the company's internal status.
- Company addresses use an optional structured object with one principal and secondary array on the company row, inheriting existing company RLS and edit permissions; retain legacy text for existing readers, isolate individual draft edits, protect the principal against silent clearing on client and server, and reuse a read-only collapsed detail view for consultation.
- Reajuste display resolves saved age bands through a read-only presentation helper; summaries use the lowest-age band per modality and history lists all stored bands, avoiding changes to billing calculations or persisted totals.
- Contracts exempt from annual reajuste (e.g. permuta) are flagged per company in `empresas.isento_reajuste`; every reajuste surface (screen list, pending alert, manual operator import, hourly operator sync) must exclude flagged contracts, and exemptions are managed in the company form instead of hardcoded per contract.
- Complaint filters use session-scoped state; duplication copies an allowlist without IDs or resolutions, and AI classification is read-only, RLS-scoped to the selected company, with human confirmation before saving.
- The complaint AI function owns a mirrored classification catalog; keep it aligned with the client catalog so suggestions cannot bypass dependent dropdown options.

- Billing totals are computed only via `src/lib/faturamento-totais.ts` (single source of truth); retroactive amounts are a subset of inclusions and must never be added again, and zero from a parsed source is a valid value, never treated as missing.
- Pagador matching never accepts a valid diverging CNPJ via name similarity; name fallback applies only when the row's CNPJ is missing/invalid, and ambiguous multi-CNPJ name matches must be flagged, not merged.


- RH PowerPoint exports use a read-only six-slide builder from the dashboard snapshot; relative performance labels compare with the displayed global mean, and strategic recommendations remain explicitly proposed, avoiding new business thresholds or persisted data.

- File billing summaries reuse the existing billing Excel parser in a read-only presentation component; never modify uploaded workbooks or persist preview results.
- Financial analysis presentation derives ordering and monthly retroactive rows from parsed results; individual history previews select the original result index without overwriting aggregate saved histories.
- The shift detail modal owns the recurrence sidebar; its inline demand form reports CPF changes while other form placements retain their embedded sidebar, preserving independent scrolling and primary content.
- Routed movement attachments retain the originating movement in their storage path while attachment rows identify the destination; reuse the same date synchronization on upload and movement save to fill only empty destination dates in the same month.
- Central NFS-e PDFs: `receber-pdf-central` queues deliveries privately, deduplicating per note/PDF separately for homologação and production; `processar-recebimento-central` validates server-side, claiming work via `nfse_central_reservar` ordered by `proxima_tentativa_em`. SIGA parsers are bundled from `src/lib/nfse-central-validador-arquivos.ts` into `_shared/siga-validador.generated.js` (regenerate with `node scripts/build-nfse-validador.mjs`; a Vitest check fails when stale). The compared fiscal value is the NFS-e gross service value, reconciled with the description, never the net; cache reuse requires an identical `chave_validacao`; the suggested movement never resolves ambiguity; destination lookups filter by normalized CNPJ, page fully and treat DB errors as failures; `nfse_central_vincular` re-checks homologação, release flag, decision, tomador, emission cutoff and revision under the per-movement advisory lock every anexo change also takes; fiscal identity is read from the PDF via `src/lib/nfse-identidade-fiscal.ts` and must match metadata; a different PDF for a received note is stored as `revisao_versao_pdf`, never auto-attached; `central_nfse` attachments are never group-shared; auto-attach stays behind `nfse_central_config.auto_anexar_reais` and homologação never attaches. Multi-spreadsheet billing is composed per tomador CNPJ in `comporFaturamento` (validation includes `retroativo`, excludes `reajuste`): duplicates only by identical hash, at most one mensalidade base, retroactives matched by competência/quantity/value, unreadable categories inconclusive; competência/período come from the movement, stored as not verified.
- Uber passengers live in `uber_passageiros` with optional default-ride fields; `uber_corridas.passageiro_id` is a plain UUID without FK on purpose — deleting a passenger must never alter ride history, which keeps its own copy of name/origin/type/reason. The ride-reason list has a single source in `src/lib/uber-passageiros.ts` (UBER_MOTIVOS), shared by the ride form and the passenger form; RLS on `uber_passageiros` mirrors `uber_corridas`.
- Life-report emails for a financial group are sent only from the group's principal contract (`contrato_principal_empresa_id`), attaching PDF+Excel of every active member, each re-validated by its own contract number server-side; member rows cannot send individually and are excluded from batch preparation, so a company never receives a split or duplicate set.
- The executivo_externo role opens the movement edit dialog read-only (fields disabled, no Save, footer "Fechar") with only "Importar do Repositório" active in the attachments section; backend gates (anexos_movimentacao RLS, anexos-movimentacoes bucket, registrar_documento_fechamento, preparar-documento-fechamento) explicitly include executivo_externo, while movement update policies remain unchanged.
